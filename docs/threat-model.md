# Threat Model and Control Register

**Scope:** `@nuxt4-layers/identity`, contract version 1.  
**Baseline:** OWASP ASVS 5.0.0 Level 2, with Level 3 requirements for access control, tenant isolation and governance where appropriate (Security Architecture §1). References are to ASVS 5.0.0 chapters; mapping to individual requirement IDs is recorded in the phase 2 verification. Data stores follow the [Data Store Security Standard v0.1](https://github.com/nuxt4-layers/platform-architecture/blob/93f3d6fb144b72d61cfb172b6a50eb6c5af9f489/docs/standards/data-store-security-v01.md); per-store evidence is in the [composition contract](composition-contract.md) §6.

## 1. Assets

- The integrity of the membership graph: who is a member of what, in which state, and who owns each group. Every access decision in the platform reads it.
- The integrity of governance: owners, settings, approval requirements, and the approvals themselves.
- The confidentiality of structure: whether an identity, group, membership or invitation exists.
- Invitation tokens, which grant membership to whoever holds them.
- The absence of personal data: what a breach of Identity's schema would reveal.

## 2. Trust boundaries

| Boundary | Trusted input | Untrusted input |
|---|---|---|
| Browser → server | Nothing | Every identifier, tenant, group, name and date in a request |
| Authentication → host → Identity | The authenticated subject, read on the server; provisioning calls from the engine's hooks | — |
| Authorisation → host adapters → Identity | Decisions, risk levels and approver qualification | — |
| Identity → host adapters → Authorisation and Profile | Directory and disclosure answers | — |
| Host → database | The `identity` schema | Other capabilities' schemas (never read) |
| Identity → outbox relay | Events (identifiers and codes only) | — |

## 3. Threats and controls

| ID | Threat | Control | Evidence | Status |
|---|---|---|---|---|
| T1 | Personal data accumulates in Identity, widening what most capabilities must handle (ADR-0005) | Only identifiers, codes, instants, digests and group names; strict schemas; every data schema listed and walked | `tests/personal-data.test.ts` | Implemented (contract) |
| T2 | Enumeration of identities, groups, memberships or invitations through errors | One coarse `forbidden` for "not found" and "not allowed"; `conflict` only after authorisation; one acknowledgement for invitation requests (V8) | `tests/contracts.test.ts` | Implemented (contract); endpoints phase 3 |
| T3 | An incomplete identity becomes active, or an unverified sign-up lingers | `pending` state outside the directory; confirmation creates the personal group atomically; expiry after 24 hours | `tests/states.test.ts`, `tests/database/provisioning.test.ts` | Implemented (phase 2a) |
| T4 | Access kept after leaving, or before starting | Effective status evaluated at read time from state, dates and identity state; directory leaves out ended and not-started memberships | `tests/states.test.ts`, conformance suite | Implemented (contract) |
| T5 | A caching directory adapter serves stale or partial membership | `strong` and `bounded` (≤ 30 s) consistency; failure rejects; conformance suite catches faulty adapters | `tests/conformance.test.ts` | Implemented |
| T6 | Self-escalation: a person makes themselves an owner, reinstates themselves or extends their own membership | No self-grant at any risk level outside one's personal group (V8) | `tests/approvals.test.ts` | Contract implemented; enforcement phase 2 |
| T7 | Approval collusion or replay: self-approval, approval by the beneficiary or a requester's service identity, approval of a different change, approval by someone who lost their role | Approver rules; strong qualification check at decision time; digest binding (V8) | `tests/approvals.test.ts` | Contract implemented; enforcement phase 2 |
| T8 | A group weakens its own governance | Approval requirements can be raised, never lowered below the floor; raising is `critical` | `tests/approvals.test.ts` | Contract implemented; enforcement phase 2 |
| T9 | Single-owner groups ungovernable, or governed without oversight | Parent-owner, tenant-owner, then published-delay routes; delay not shortenable, announced, cancellable | `tests/approvals.test.ts` | Contract implemented; enforcement phase 2 |
| T10 | Session theft used for sensitive changes | Step-up by risk for requesters and approvers, including in one's own personal group; the risk is the higher of Identity's and the host catalogue's | `tests/approvals.test.ts`, `tests/database/approvals.test.ts` | Implemented (phase 3a) |
| T11 | Privilege gained through the hierarchy, e.g. by reparenting under a group whose administrators should not see it | The hierarchy confers nothing; reparenting is `critical`, same tenant only, cycle-checked, depth-limited; the database refuses a cross-tenant parent, a cycle or a depth beyond 32 whatever the caller | `tests/states.test.ts`, `tests/database/groups-and-memberships.test.ts`, `tests/database/approvals.test.ts` | Implemented (creation phase 2b; reparenting, with the moved group's descendants counted against the depth, phase 3a) |
| T12 | Supply-chain compromise | Runtime dependency `zod` only; `minimumReleaseAge`, `blockExoticSubdeps`, frozen lockfile, dependency review | `pnpm-workspace.yaml`, workflows | Implemented |
| T13 | Homoglyph and invisible-character group names used to impersonate a group | Safe names: NFC, forbidden code points, single-script rule; confusable skeleton for siblings, unique per parent in the database | `tests/safe-names.test.ts`, `tests/database/groups-and-memberships.test.ts` | Implemented (phase 2b) |
| T14 | Invitation tokens stolen from the database, guessed or brute-forced | 256-bit tokens; only SHA-256 digests stored; single use; 14-day expiry; rate limits on creation and acceptance | `shared/invitation.ts`, `tests/database/joining.test.ts` | Implemented (phase 3b): tokens generated on the server and returned once; only digests stored; every acceptance or decline counted against the per-identity limit, real token or not, and answered alike |
| T15 | An invitation forwarded to someone else is accepted | Invitations to an existing identity are bound to it. Unbound invitations wait for an administrator to confirm who accepted when the group's `invitationAcceptance` is `confirm` (the default for guests); nobody confirms their own acceptance; the inviter is told of every acceptance | `tests/invitations.test.ts`, `tests/database/joining.test.ts` | Implemented (phase 3b), including no self-admission by the inviter. Residual risk for member invitations left `immediate`, see §4 |
| T16 | Missing port leads to an implicit permissive store, decision or dropped event | Required ports fail closed (ADR-0002) | `tests/composition.test.ts` | Implemented |
| T17 | Cross-tenant access through Identity's own store | Tenant on every isolated row; row-level security on the transaction-local `identity.tenant_ids`, nothing visible without it; runtime role owns nothing, has no `BYPASSRLS` (refused at migration) and no grant on cross-tenant tables, which it reaches only through narrow SECURITY DEFINER functions with a fixed `search_path` (ADR-0006 §5) | `tests/database/foundation.test.ts` | Implemented (phase 2a, writes 2b) |
| T18 | Lost or duplicated lifecycle events break revocation or erasure | Transactional outbox; at-least-once delivery; consumers idempotent by event identifier and version; access never depends on an event | `shared/events.ts`, `tests/database/provisioning.test.ts` | Implemented (phase 2a): events written in the same transaction as the change; relay claims with `FOR UPDATE SKIP LOCKED`, publishes in order, marks only after success, never twice under concurrency, never publishes a malformed event |
| T19 | A group name identifies a person ("Alice's book club") | Group names never appear in events, logs, directory or disclosure answers; personal groups have no name; a valid correction or erasure request about a group name is met by a rename (iam-integration data-subject requests); administration pages advise against personal names | `tests/personal-data.test.ts` | Accepted risk with treatment, see §4 |
| T20 | Break-glass misuse | Break-glass identity kind; passkey only; three actions; never self-appointment; alert on every use; review closed by another person (ADR-0007) | `tests/approvals.test.ts` | Contract implemented; enforcement phase 2 |
| T21 | Impersonation ("act as") | Not provided by any port or function (ADR-0005 §2.2) | Architecture | Implemented |
| T22 | Unsafe policy changes by a host | Hard bounds; loosening past a default needs a risk-treatment reference | `tests/policy.test.ts` | Implemented |
| T24 | SQL injection, or a definer function used to read beyond its port | Hand-written SQL is parameterised throughout; schema and role names are validated identifiers; definer functions take typed arguments, fix `search_path`, schema-qualify every name and return only a port's fields; answers are parsed with the contract before leaving the layer | `tests/database/foundation.test.ts`, `tests/database/directory.test.ts` | Implemented (phase 2a) |
| T25 | A compromised or buggy runtime writes beyond its purpose: a root group, an owner, a protected column, an unannounced change, a forged event | Column-level `UPDATE` grants; guard triggers refuse root and personal groups and any ownership except the actor as founding owner of a group created in the same transaction (phase 3a: a different founding owner, for a root group, is claimed only through a table the runtime role cannot write); events written by SECURITY DEFINER triggers from real row changes, never by the runtime role; a change without a correlation identifier is refused | `tests/database/groups-and-memberships.test.ts` | Implemented (phase 2b) |
| T26 | Disclosure context reveals groups the viewer is not in | Facts limited in SQL to the viewer's own groups and tenants and the group context; a group context the viewer is not in is ignored; answers parsed with the contract | `tests/database/groups-and-memberships.test.ts` | Implemented (phase 2b) |
| T27 | Governance changes made without the approval they need: a self-grant, an approval by the requester, the beneficiary or someone no longer qualified, an approval of a different change, or a change applied after its rules stopped holding | `refuseRequest` and `refuseApproval`; qualification read from Authorisation (`strong`) when the approval is given; approvals bound to a digest the database computes over everything the change does and checks again before applying; every rule checked again when the change applies, otherwise it is rejected; changes expire unapproved after 7 days | `tests/approvals.test.ts`, `tests/database/approvals.test.ts` | Implemented (phase 3a) |
| T28 | A compromised or buggy runtime forges, approves or applies a governance change directly | Pending changes are read-only to the runtime role; recording, deciding, cancelling and applying run through SECURITY DEFINER functions that refuse a risk below Identity's, a requirement below the group's, a self-grant, a missing justification, a short published delay, and approvers who are the requester or beneficiary, inactive, deciding twice or (for the owner fallbacks) not owners now; a guard trigger refuses reviving an ended membership, reinstating a suspended one, and suspending or removing an owner; only the migration role creates tenants and a tenant's first root group | `tests/database/approvals.test.ts`, `tests/database/foundation.test.ts` | Implemented (phase 3a). Residual: on the `approvers` route the database relies on the layer's strong read of Authorisation, which it cannot see |
| T29 | Nobody can approve, so a group can never change, or one person changes it alone at once | Fallbacks to one owner of the parent group, then of the tenant's root group; otherwise a published delay (72 or 168 hours) the requester may cancel but not shorten, announced by `approval.requested` | `tests/database/approvals.test.ts` | Implemented (phase 3a) |
| T30 | Joining used to enter or probe groups outside one's reach | Join requests and open joining only within one's tenant (home tenant or a membership in effect); other tenants' and unknown groups alike `forbidden`; one open request per person and group; nobody decides their own; membership conditions checked again when it is created | `tests/database/joining.test.ts` | Implemented (phase 3b) |
| T23 | Correlation lost across members, so a process cannot be audited | Correlation identifier on every port call, pending change and event | `shared/events.ts`, `shared/ports.ts` | Implemented (contract) |

## 4. Deferred controls and risk treatments

| Gap | Risk | Treatment |
|---|---|---|
| No HTTP endpoints or default pages yet | Hosts must build their own administration over the server functions | Phases 4 and 5 |
| The identity lifecycle, orphaned-group recovery, the recovery hold and break-glass actions not yet enforced (T20) | Those processes cannot run yet; nothing weaker runs in their place | Phase 3c |
| A group that raised a requirement to two approvers, but has fewer than two other qualifying principals, falls back to one owner of its parent group or of the tenant's root group (T29) | One person outside the group approves where the group asked for two | Taken in phase 3a (design decisions §13) for the project owner's review: the fallback applies only when the group cannot meet its own requirement, the fallback owner already governs above it, the change waits for that owner rather than applying alone, and every step is announced |
| Confusable data is a subset of UTS #39 | Rare look-alikes pass the sibling check | Phase 2 server code may load the full confusables table; mixed-script names are already refused |
| Bearer invitations left `immediate` (T15) | A forwarded member invitation admits someone other than the intended person | Treated 2026-10-09 (design decisions §11): guests need confirmation by default and any group can require it for members. Remaining risk, for member invitations a group leaves `immediate`, is accepted: 14-day expiry, single use, the inviter is told who joined and can remove them, and invitations to existing identities are bound |
| Group names can name a person (T19) | Personal data in an organisational field | Accepted with treatment 2026-10-09 (design decisions §11): names are needed for groups to be usable. Contained (safe names only, never in events, logs or port answers; personal groups have none). Profile's erasure does not reach them, so a valid correction or erasure request is met by the owners renaming the group (`identity.groups:rename`, `medium`), or by a platform operator with a reason code if the owners have not acted within half the request's deadline. Administration pages (phase 5) advise against personal names and warn when a name matches its creator's display name |
